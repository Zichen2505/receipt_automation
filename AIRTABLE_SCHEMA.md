Keep the existing base name, table name and five field names unchanged.
Add exactly one field: ReceiptID (single line text, non-primary).
Vendor remains the primary field. ReceiptID is an application identifier;
the backend must enforce uniqueness and prevent duplicate synchronization.

| Airtable field name (exact case) | Type | Backend source | Meaning |
|---|---|---|---|
| Vendor | Single line text; primary | data.merchant | Merchant name |
| Date | Date; no time | data.date | Receipt issue date, YYYY-MM-DD |
| Amount | Number; 2 decimal places | data.total | Printed final total, not subtotal or balance due |

```json
    "serialize_json(data)": "RawJSON"
  }

```

The backend API and evaluation JSON retain their existing snake_case names.
Only the Airtable adapter maps to the exact Airtable names above.
RawJSON is a JSON string, not an object supplied directly to a text field.
It preserves receipt_number, subtotal, tax, tip, discount, items and all other
agreed extracted fields, with original decimal strings and null values.
Amount is sent as a JSON number; arithmetic is performed with Decimal before
serialization. Do not use Airtable numeric values as the calculation authority.

## Sync and evaluation rules

- Local storage retains the original PDF, extraction, validation and notification events.
- Only status=saved with validation.passed=true may be synchronized to Receipts.
- F and G remain local with status=needs_review; they must not create Airtable rows.
- With a clean table, all seven evaluation cases should create five non-empty receipt rows.
- Repeated submissions must not create extra rows. Save the returned Airtable rec... ID locally.
- ReceiptID is distinct from both the merchant's receipt_number and Airtable's rec... ID.
- RawJSON preserves the complete data object; it is not the PDF file or the model's unparsed prose.
- Do not create approvals, budgets, line-item tables or notifications tables for this demo.
- Base ID and Table ID are UNKNOWN until obtained from account metadata or a clear account URL.
- Never infer API credentials or store secrets in this document.

## Unified output contract and evaluation coverage — v1.1

The final HTTP response has a non-empty backend-generated receipt_id, status, data,
and validation. Different PDF samples must have different receipt_id values.
A repeated upload of identical PDF bytes must reuse the existing receipt_id;
this repeat-request behavior requires a live API test.

The data object always contains merchant, date, receipt_number, currency,
total, subtotal, tax, tip, discount and items. Item objects contain description,
quantity, unit_price and amount. Missing optional values are null, not zero.
The API uses decimal strings for money; only Airtable Amount uses a JSON number.

The eval v1.1 scorer checks content, validation, non-empty system IDs and ID
uniqueness across distinct PDFs. The optional --airtable-records input verifies
all six columns against a real, fully fetched Airtable record snapshot and
checks that RawJSON parses to the entire data object without lost fields/items.
It rejects anomaly rows, missing rows and duplicate ReceiptID rows. An entirely
empty starter row is ignored. Use a dedicated demo table or a correctly scoped
run snapshot; unrelated existing receipt rows are reported as unexpected.

No real model API, live application API or Airtable run has yet been verified.
The evaluation script cannot prove a snapshot is authentic; obtain it from
the actual Airtable API and never construct it from expected answers.
The 7 PDF inputs and their field answers are unchanged from eval v1.0.
The previous scorer accepted missing receipt_id; v1.1 closes that gap.
Airtable physical field names are unchanged. Remote ReceiptID creation remains
unconfirmed, as recorded in the screenshot-observed state above.
